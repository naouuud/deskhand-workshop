Think of the nurse at a hospital entrance. She doesn't treat you: she decides which queue you join and how fast. Our triage step does the same for support tickets. It reads one ticket and returns four labels, and every later step of Deskhand reads those labels.

Why start here? A wrong label sends a ticket to the wrong queue. It never sends money. That makes triage the safest step to make trustworthy first.

A prompt has up to five parts. The role says who the model is. Instructions say what to do. Context is the material it reads (here, the ticket). Examples are worked cases. The output contract is the shape the answer must have.

In triage.py the role and instructions live in SYSTEM_PROMPT, sent as the system message: the part of the request that sets the rules. The ticket goes in a separate user message. Read the priority rule there: "legal threats are urgent" is a business decision written in English, so it deserves the same review as code.

Two things are missing: there are no examples, and the prompt never mentions JSON, field types or allowed values. A useful comparison: the prompt is the docstring, the output contract is the type signature.

The prompt never names the four keys, yet every answer has exactly those four. Something besides the prompt text travels with the request.

Option 2. In llm.py we pass the SDK a Python class with the four fields (TriageResult, as response_format). The SDK turns it into a description of the shape and sends it along. The hint shows it: the system prompt (126 tokens) plus the ticket (73) make 199, but we were billed for 392. The extra 190 or so tokens are that description plus message wrapping.

Option 1 is tempting because it often works, and "often" is how v1's ticket A happened. Option 3 is exactly what v1 did: json.loads on whatever came back. One consequence: deleting sentences from the prompt won't break the shape, because the shape doesn't come from the prompt.

One job per stepSmall prompts beat one giant prompt

A function that does four things vs four small functions. Each small one can be tested alone, swapped for a cheaper model, and debugged when it breaks.

v1 asked one prompt to do four jobs at once: label the ticket, reason about policy, compute the refund and write the reply. It did all four badly, and when it failed you couldn't tell which job had gone wrong.

Splitting the work into steps is called decomposition, and you already do it in code: four small functions instead of one that does everything. Each step gets one job and one output shape, so you can test it alone, price it alone, swap in a cheaper model, and debug it when it breaks.

Look at the green box: Validate is ordinary code, not another prompt. Checking a model's answer is plain Python. Today's code builds only the first box, triage. The picture is simplified.

The problemHow prompts fail without throwing an exception

The rules get ignored

A long thread pushes the instructions far away. The model quietly drops "be honest about confidence".

It says sorry instead

"I'm sorry, I can't help with that." v1 sent these to customers. Incident #2.

It invents fields

It wraps the JSON in chatter

None of these raise an error by themselves. Code that trusts the output just carries on with bad data.

Calling a model is different from calling a database. A failed call usually doesn't throw an exception. It returns something, and the something is wrong. So failure is a normal output of an LLM call, and the engineering is what your code does after the call returns.

Structured outputsFrom "please return JSON" to a checked contract

0 · Ask nicely

"Respond with JSON" in the prompt. Deskhand v1.

Guarantees nothing.

1 · JSON mode

A provider setting.

Valid JSON, any shape.

2 · Send the shape

A schema, a description of the keys, types and allowed values, travels with the request.

The answer comes back in that shape.

3 · Check it yourself

Your code checks the answer against the same shape before using it.

Nothing reaches your code unchecked.

A web form with dropdowns. The dropdown stops most typos (level 2), but your server still validates the submission (level 3), because you never trust the browser.

Four levels of control over the answer's shape. Level 0 is a request in the prompt; nothing enforces it. Level 1, JSON mode, is a provider setting that guarantees valid JSON but lets the model pick any keys. Level 2 is what providers call structured outputs: a schema travels with the request and the model's answer is held to it. Level 3 is your own code checking the answer against the same shape after it arrives.

Deskhand uses levels 2 and 3 together, for the same reason your server re-checks a form even though the browser had dropdowns: you never trust the other side of the network, and providers differ in what they enforce.

Neither level checks meaning. A confidence of 0.9 on a nonsense label passes both. The schema format is called JSON Schema; slide 33 shows ours.

Pydantic: a Python library. Describe data as a class with type hints; it checks incoming data and raises an error if it doesn't fit.

One class, two jobs: it becomes the shape sent to the model, and it checks the answer that comes back.

Pydantic is the Python library that does level 3. You describe data as a class that inherits from BaseModel, with type hints on each field, and Pydantic checks incoming data against it. Validation is that check: data that doesn't fit raises an error instead of turning into an object.

Literal[...] means "exactly one of these values". So "refund-ish" is more than discouraged: no TriageResult can hold it. (An Enum class would do the same job with more code.)

One class, two jobs: the SDK turns it into the schema sent to the model, and it checks the answer that comes back. Read the comment on confidence before the next slide. The full class, with its comments, is in models.py.

Each line changes one field and keeps the other three valid. The question is what TriageResult actually enforces, which can differ from what its comments promise.

A is rejected: category is a Literal and "refund-ish" is not one of the six values. B is accepted: the field is a plain float, and the "0..1" is only a comment, so 1.7 walks straight in. C is rejected with "unable to parse string as a number".

B is the lesson: a comment is not a constraint. Today's checkpoint really has this gap. Pydantic can enforce a range, for example Field(ge=0.0, le=1.0), but the field has to say so. On C: the problem is that "high" isn't a number. The string "0.9" would be accepted, because Pydantic converts numeric strings by default.

Put the two emails side by side. T-1003 says nothing about what is wrong or what Omar wants. T-1019 says everything: one bulb of four strobes, he tried the fixes, he wants one replacement. The confidence gap between them is a tenth, while the prompt asks for low confidence on vague tickets.

Which check would have caught T-1003's 0.8? None of them. The schema and Pydantic check the shape, and 0.8 is a valid number. Only comparing the real answer with what we wrote down in advance ("vague, so below 0.5") catches it. Running real tickets and comparing answers against expected ones is called an evaluation, or eval.

Confidence is a number the model writes, not a measured probability. That matters for anything that routes low-confidence tickets to a person: an overconfident vague ticket skips that person.

The mantraTwo rules: check every answer, never show users a raw error

Never trust LLM output directly.
Never expose raw failures to users.

"Never trust", in practice

Every answer passes TriageResult before any later step reads it. "refund-ish" never gets past that check.

"Never expose", in practice

The customer reads a sentence we chose. Engineers read an error code in the log. Never str(exception).

These two rules come back in every session. "Never trust": nothing in our code reads a model answer until it has become a TriageResult. "Never expose": when something fails, the customer reads a sentence we wrote, and engineers read an error code in the log. main.py prints errors.user_message(code), never str(exception), because exception text is written for engineers and can leak provider details.

Ticket C in Session 1 broke "never trust". The bot offered a $249.99 refund because the model said so, and no code compared it with the $24.99 order.

Careful: Pydantic alone wouldn't have saved ticket C. A refund amount of 249.99 is a valid number. Catching it needs code that compares the amount with facts we own, like the real order total. Valid is not right, again.

The repair loopWhen the answer doesn't fit: ask once more, then give up

An expense report sent back once with the error circled. If the second try is still wrong, it goes to a person, not round and round forever.

A repair is a second attempt that tells the model what was wrong with the first. The loop is bounded: a fixed limit of one repair, so at most two model calls per ticket. In triage.py that limit is MAX_REPAIR_ATTEMPTS = 1.

Compare v1's retry (incident #4): it resent the identical request, so it usually failed the same way. Our repair adds the error message to the conversation, like an expense report sent back with the mistake circled.

Why only one? Each attempt is a paid call, and a person is the fallback anyway. Only a malformed answer gets repaired. Rate limits and timeouts are passed up with their own codes, because asking again more clearly can't fix a busy server.

TestsTesting our code without calling the model

A test is a small function that runs our code and checks what it did. pytest finds every function whose name starts with test_ and runs them all. Every test here has the same three parts.

1 · Put in a fake model

A tiny function we wrote, standing in for the real model call. It answers the way this test needs, the same way every time.

2 · Run our real code

Call triage on a ticket, the same call the batch run made. Triage can't tell the fake from the real model.

3 · Check what happened

Each check is one claim: the right error came out, the fake was called exactly twice. One false claim and the test is red.

A crash-test dummy. Nobody puts a real driver in the car for every test: the dummy behaves the same way on every run, so what you learn is about the car. The fake is the dummy, our triage code is the car.

Why no real model? It can answer differently each time, and a test must give the same result every time. Also: no internet, no API key, no cost.

A test is a small function that runs our code and checks what it did. pytest is Python's usual test runner: it finds every function whose name starts with test_, runs each one, and prints passed or failed for it.

Our tests never call the real model. A real model can answer differently each time, and a test must give the same result on every run, or you could never tell whether a red test means a bug in our code or a different answer from the model. So every test here has three parts: a fake model (a tiny function that answers the way the test needs), a run of our real triage code (which cannot tell the fake from the real model), and checks, each one a claim about what happened. The next slide shows one of these tests in full.

Live demoThe test for "exactly one repair", line by line

def test_repair_exhausted(monkeypatch):
    call_count = 0

    # 1 · The fake model: counts its calls, always gives a broken answer
    def fake_completion(messages, response_model, **kwargs):
        nonlocal call_count
        call_count += 1
        raise errors.DeskhandError(errors.LLM_MALFORMED_OUTPUT, "still not valid")
    monkeypatch.setattr(llm, "structured_completion", fake_completion)

    # 2 · Run our real triage code. We expect it to give up
    with pytest.raises(errors.DeskhandError) as excinfo:
        triage.classify_ticket(TICKET, request_id="req-3")

    # 3 · Check: the right error, after exactly 2 calls
    assert excinfo.value.internal_error_code == errors.REPAIR_EXHAUSTED
    assert call_count == 2

The odd words

monkeypatch.setattr(…): use the fake instead of the real model call, in this test only.

nonlocal: lets the fake add to call_count, which belongs to the test.

**kwargs: accept any extra arguments and ignore them.

pytest.raises(…) as excinfo: an error must happen inside this block. excinfo keeps it for the checks.

assert: a claim. If it's false, the test fails.

From tests/test_triage.py, minus its docstring and comments.

This is the third of the four repair-loop tests in tests/test_triage.py, in full. Part 1 is the fake model: it counts how often it is called and always raises the "broken answer" error, so no repair can ever succeed. monkeypatch.setattr swaps it in for the real model call, for this test only, and puts the real one back afterwards. It works because triage.py calls llm.structured_completion through the llm module.

Part 2 runs the real triage code inside pytest.raises, which means "an error must happen here" and keeps that error in excinfo. Part 3 makes two claims: the error code is REPAIR_EXHAUSTED, and the fake was called exactly twice (the first try plus one repair). The right column explains the Python words you may not have met.

ExamplesZero-shot vs few-shot

Zero-shot

Instructions only, no examples. Start here: it is the cheapest, and current models are good at it.

Today's triage: 392 input tokens.

Few-shot

Instructions plus 1–3 worked examples: a ticket and the answer you want for it.

3 examples ≈ 300 more tokens: input grows by three quarters.

Training a new colleague. You can explain the form, or you can also show them three forms that were filled in correctly. The examples help most with the odd cases.

The price: 300 tokens × $0.40 / 1M × 10,000 tickets = +$1.20 a month. Small, but paid on every call.

"Shot" just means example. Zero-shot means instructions only, like today's triage. Few-shot means instructions plus one to three worked examples: a ticket and the answer you want for it.

Each example costs about 100 tokens (a ticket of about 75 plus a 25-token answer), and you pay it on every call, not once. Three examples add about 300 tokens to the 392 we send now: input grows by three quarters. At 10,000 tickets a month that is 300 × $0.40 / 1M × 10,000 = $1.20.

A sensible rule: start zero-shot, and add an example only when a specific ticket fails without it. Build examples from your own hard cases (a vague ticket, an angry one), not invented ones, and judge the result on other tickets.

In code, an example is a fake earlier turn of the conversation. A user message holds an example ticket, then an assistant message holds the answer we want, and only then comes the real ticket. The model sees a conversation where it already answered once in that style, and follows the pattern.

The warning is about fair testing. Once a ticket is an example, the model has seen its answer, so a good score on it proves nothing, like grading a student on the exact question you solved for them. Chain-of-thought"Think step by step": when it pays, when it doesn't

Chain-of-thought: asking the model to write out its reasoning before the answer. That reasoning is output tokens, so you pay for it and wait for it.

Worth it

Steps that build on each other: refund maths, or two policies that disagree (14 days vs 30 days).

Waste of tokens

Picking a label. Triage usually gets no more accurate, only slower and more expensive.

About 150 extra output tokens × $1.60 / 1M = $0.00024. The call goes from $0.000195 to $0.00044, and gets slower.

With a fixed schema, the reasoning needs its own field, placed before the answer fields.

Chain-of-thought helps when each step builds on the one before: arithmetic, or two rules that disagree (like a 14-day window in one policy and a 30-day window in another). Writing the steps out gives the model something to build on. Picking one label from six has no steps, so reasoning there mostly adds cost.

The price: about 150 extra output tokens at $1.60 per million is $0.00024, so a triage call goes from $0.000195 to $0.00044, about 2.2 times, and it gets slower, with nothing measurably better.

The schema detail matters. Our TriageResult has four fields and nowhere to write reasoning. You would add a reasoning field placed before the answer fields, because the model writes fields in order: reasoning written after the answer can't influence it.

Structured outputsThe schema the model is held to

A JSON Schema is a JSON document that describes other JSON: which keys must be there, the type of each, and the allowed values.

{"title": "TriageResult", "type": "object",
 "properties": {
   "category":   {"type": "string", "enum": ["refund_request", "replacement", …]},
   "priority":   {"type": "string", "enum": ["low", "medium", "high", "urgent"]},
   "sentiment":  {"type": "string", "enum": ["calm", "frustrated", "angry"]},
   "confidence": {"type": "number"}},
 "required": ["category", "priority", "sentiment", "confidence"]}

Not written by hand: TriageResult.model_json_schema() generates it.

This is what the SDK sends to the provider for TriageResult. Read it like a spec: "type": "object" means a JSON object; properties lists each field and its type; "enum" means one of these values only, which is where Literal ends up; required lists the fields that must be present. The SDK also forbids extra keys and turns on strict mode.

Nobody wrote it by hand. TriageResult.model_json_schema() generates it from the class, so the schema and the check can never drift apart. The slide trims the category list and some titles.

Look at confidence: just "number", with no minimum or maximum. That is slide 11's 1.7 gap, in writing. This schema is also most of the extra 190 or so tokens on every call.

The wrapperllm.py: the only file that talks to the provider

def structured_completion(messages: list[dict], response_model: type[BaseModel],
                          model: str | None = None, temperature: float = 0.0,
                          max_output_tokens: int = 1024) -> tuple[BaseModel, Usage]
  • Returns a checked TriageResult plus Usage: prompt tokens, output tokens, cost.
  • The defaults are decisions: temperature 0, output capped at 1,024 tokens.
  • Works with Azure, OpenAI or Anthropic (LLM_PROVIDER in .env). No other app file imports a provider SDK.
  • Provider errors become our own error codes before they leave this file.

The one class in your app that talks to Stripe. Swap the payment provider, or fake it in tests, and only that file changes.

A wrapper is one module that hides an outside service behind your own function. Here every model call goes through structured_completion in llm.py, which returns the checked object plus a Usage: prompt tokens, output tokens and cost.

The defaults are decisions. Temperature 0 (from Session 1) picks the most likely answer, which is what you want when a program reads the output. The 1,024-token output cap is the setting the break-it demo turned down to 10. LLM_PROVIDER in .env picks azure, openai or anthropic; on Anthropic the cap is raised to at least 16,000.

Because only this file talks to the provider, swapping providers, or faking the model in tests, touches one file. Provider errors are turned into our own codes before they leave it.

RepairThe loop in triage.py

for attempt in range(1, MAX_REPAIR_ATTEMPTS + 2):    # 1 + 1 = two tries at most
    …  (start a timer)
    try:
        result, usage = llm.structured_completion(messages, TriageResult)
    except errors.DeskhandError as exc:
        if exc.internal_error_code != errors.LLM_MALFORMED_OUTPUT:
            raise  # rate limits, timeouts etc. are not fixable by re-prompting
        …  (log "triage.repair")
        messages.append({"role": "user", "content": "Your previous response was not a valid "
            f"TriageResult ({exc.detail}). Respond again with ONLY the required fields."})
        continue
    …  (add this call's cost, log "triage.completed")
    return result, cost_usd
…  (log "triage.failed")
raise errors.DeskhandError(errors.REPAIR_EXHAUSTED, ...)

Example: first answer "confidence": "high" → repair says "…(confidence was the string 'high')…"

range(1, MAX_REPAIR_ATTEMPTS + 2) with a limit of 1 gives attempts 1 and 2: the first try plus one repair. Only LLM_MALFORMED_OUTPUT is repaired. Any other code is re-raised at once by the bare raise.

On a malformed answer, the error detail becomes part of a new user message, then continue goes round again. The bad answer itself is not sent back, only the description of what was wrong. If both attempts fail, the loop logs triage.failed and raises REPAIR_EXHAUSTED.

Two details. The "high" example is the detail used in tests/test_triage.py; with a strict schema a real model can't send it, so the test fakes it. And cost is only added after a successful call, so a failed attempt's tokens never reach the reported cost, though the provider billed them.

Failures with namesThe error codes triage can raise

CodeWhenWhat triage does
LLM_MALFORMED_OUTPUTThe answer doesn't fit the schema, was cut off, or was a refusalAsks again, once
REPAIR_EXHAUSTEDThe second answer is bad tooGives up; the ticket goes to a human
LLM_RATE_LIMITED, LLM_TIMEOUTThe provider is busy or slowPasses it up unchanged
INTERNAL_UNEXPECTEDAnything else: bad key, content filterPasses it up unchanged
  • errors.py holds 13 codes. Triage uses these five; the rest arrive with later steps.
  • A named error can be counted and alerted on. except: pass can't.

An error taxonomy is a fixed list of named error codes, like HTTP status codes for your own system. Each code tells the caller what to do: repair it, give up and hand over to a person, or pass it up. That is why there are several codes instead of one "LLM_ERROR".

errors.py defines 13 codes in total; triage raises these five. Every code becomes a customer sentence through user_message, and the code itself stays in the log.

Why bother? A named error can be counted, graphed and alerted on ("REPAIR_EXHAUSTED doubled today"). An except: pass leaves nothing to count. One edge case: a missing API key raises a plain RuntimeError from llm.py, so it crashes with a stack trace instead of becoming a FAILED row.

def test_malformed_then_repaired(monkeypatch):
    calls = []
    def fake_completion(messages, response_model, **kwargs):
        calls.append(list(messages))
        if len(calls) == 1:
            raise errors.DeskhandError(
                errors.LLM_MALFORMED_OUTPUT, "confidence was the string 'high'"
            )
        return RESULT, USAGE
    monkeypatch.setattr(llm, "structured_completion", fake_completion)
    result, cost_usd = triage.classify_ticket(TICKET, request_id="req-2")
    assert len(calls) == 2            # + 4 more asserts, 2 before and 2 after

Read the test top to bottom. The fake records every conversation it receives (list(messages) takes a copy, because triage keeps adding to the same list). On the first call it raises a malformed-output error; on the second it returns a good result. The test then checks the result, the cost, that there were two calls, and that the repair message is a user message carrying the error text.

With MAX_REPAIR_ATTEMPTS = 0, test_malformed_then_repaired fails because the first error ends the run with REPAIR_EXHAUSTED, with no second chance. test_repair_exhausted fails because it sees 1 call instead of 2. The other two never depend on a repair. Set it back to 1 and you get 18 passed again.
