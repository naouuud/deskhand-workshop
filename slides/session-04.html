LLM Application Architecture

From a script to a service: one state object, clear statuses, live progress, and surviving a crash

Session 4 · Week 2 · Monday, October 26, 2026

Session 4 of the Deskhand workshop. Until now Deskhand was a script: you ran it, waited, and it printed an answer. Today it becomes a service: a program that keeps running, takes tickets over HTTP and answers at once. Everything is in checkpoints/02-service.

TodayDeskhand becomes a service

Support agents don't use terminals. A service takes a ticket, answers at once, does the work in the background, and lets a screen follow along.

  1. One record holds the whole run. Its status only moves along fixed arrows.
  2. Save after every step. A crash resumes instead of starting over.
  3. Stream progress, never half an answer. A viewer who leaves loses nothing.

How today works: no typing in class. You predict before every run, vote when a refund needs a person, and call the moment we pull the plug. Incidents in play: #3 and #10.

A support agent works in a browser, not a terminal, so Deskhand needs an HTTP API that a screen can call. The three ideas on this slide are the three blocks of the session. One record per run: everything Deskhand knows about a ticket lives in one object, and its status can only move in fixed ways. Save after every step: if the server dies, the run carries on from the last step that finished. Stream progress: the screen sees each step as it happens, but never a half-written plan.

The incidents in play are two from Session 1's list: #3, partial failures streamed to the support agent's screen, and #10, nobody can debug why a specific run failed. A longer, file-by-file version of the whole session is in handouts/session-04-walkthrough.md.

AnatomyA real LLM service, box by box

A restaurant order. The waiter gives you a number straight away, the kitchen cooks in the back, and the screen above the counter shows "preparing", then "ready". Nobody stands at the counter holding the line open.

Read the diagram left to right. The agent's screen (the lab, or curl in a terminal) sends POST /tickets. The FastAPI app in app.py answers in milliseconds with a request ID, a short name for this run, and that is all the request does. The real work, eleven steps, runs in a background thread (a second line of execution inside the same program), started by graph.run_in_thread. Two kinds of step call out: to the LLM API, and to the order API on port 9000. After every step the run is saved to SQLite in runs.db, and events flow back to the screen and into logs/runs.jsonl.

Why not do the work inside the request? A run takes seconds of model calls. Holding an HTTP request open that long ties up a connection and breaks on any proxy timeout.

Idea 1The state object holds the whole run

A state object is one Pydantic object per run. Each step reads it, does one job, writes its result into it, and hands it on. After every step it is saved to SQLite.

  • No globals: if it isn't in the state, the next step can't see it.

A GitHub Actions run page: each step's status and log are kept, so you see exactly where it stopped. The state object is that page for one ticket.

A state object is one Python object that holds everything about one run. In Deskhand it is TicketResolutionState in models.py, a Pydantic model like the TriageResult you already know. Each step gets the state, does one job, writes its result into it and hands it on. Nothing is kept in global variables, so if a value isn't in the state, the next step can't see it, and neither can you when you debug.

The payoff: "what happened to run 3f9c1a2b7d4e?" becomes one lookup of the saved state instead of a hunt through logs, the way a CI run page shows you exactly which step stopped.

    ticket_id: str                   # "T-1001"

    customer_match: bool | None      # True: order O-48291 is Dana's
    triage: TriageResult | None      # Session 2's triage answer

    policy_chunks: list[dict]        # empty in this checkpoint
    resolution_plan: ResolutionPlan | None   # the plan: actions and refund amount
    ...                              # repair and approval fields
    customer_reply_draft: str | None # text for the customer
    internal_note: str | None        # text for the support team

Fields start empty and fill in as the steps run. A saved copy tells you exactly how far a run got.

Read the fields top to bottom and you are reading the run in order. request_id, ticket_id, ticket_text and customer_name are set by POST /tickets before the run starts, and customer_name comes from tickets.json, not from the text the model reads. Then each step fills its own field: triage by the triage step, order_data and customer_match by fetch_order_data, resolution_plan by the planner.

Because fields start empty and fill in step by step, a saved copy dates a crash: triage filled and order_data empty means the run died fetching the order. The last two fields are kept apart on purpose. The reply goes to the customer and the internal note to staff, so one can't be sent as the other by accident. The rest of the fields are on slide 26.

Idea 1Deskhand's workflow: eleven nodes

Each step is a node: it reads the state, does one job, and names the next node. Failure is a node too.

A node is one step of the workflow: a Python function in nodes.py that takes the state, does one job and returns the name of the next node. The colours say what each one touches. Four call the LLM: triage, the planner, the repair and the reply. Two call the order API: the lookup and the refund. The ones that decide, like validate_plan, are plain code. approval_gate waits for a person.

Failure is a node too. Any node that raises an error is routed to handle_failure, which ends the run with a safe message instead of a stack trace. No run visits all eleven: T-1004 runs eight, T-1001 nine, counting the gate. Section 4 of handouts/session-04-walkthrough.md goes through the nodes one by one.

Idea 1The status field is a state machine

A state machine: a fixed list of statuses and the only moves allowed between them. Every run ends in completed or failed, written down.

"Plan broke a rule": our code found a problem in the plan, such as a refund above the order total.

status is a field with seven allowed values, and a state machine is that list plus the moves allowed between them. Trace T-1004, Lena's $45 keyboard: queued, running, executing (no approval needed), completed. Trace a plan that keeps breaking a rule: running, needs_repair, re-checked, still broken after two repairs, failed.

Every run ends in completed or failed, saved in the database, never guessed from a closed connection. One surprise: a run a person rejected ends completed, not failed. It finished its job, and the reply tells the customer a person will follow up. "Over $50" is the usual reason to stop for a person; rules.approval_reasons has the others, such as any replacement. The arrows are a rule the nodes follow, not a check: _set_status in nodes.py would write any of the seven values.

Idea 2Save after every node

Save the state

One "save or replace" of the run's row: about 10 ms on a Windows laptop (measured, 200 saves).

Redo the plan

One planner LLM call: about 3 s and about $0.0005 in our runs. Plus whatever the model decides differently this time.

  • Saving after every node costs about a tenth of a second per run.
  • Crash mid-run? Restart and continue from the last saved node. Finished nodes don't run again.
  • Debugging a failed run means reading its saved state, not guessing.

Is saving after every node worth it? Compare the two cards. A save writes one row, about 10 ms. Redoing one planner call costs about 3 s and about $0.0005, and the model may answer differently the second time. Across a whole run the saves add up to about a tenth of a second. What you buy: a crash loses at most the node that was running, and a failed run can be read instead of guessed at. The line is store.save_state(state, next_node=...) in graph.run, right after each node returns.

Don't confuse the save with the log. logs/runs.jsonl is history for people, appended line by line. The row in runs.db is the current state a program resumes from. Deskhand keeps both.

The runs table in runs.db has one row per run: its status, the next node to run, and the whole state as JSON. The row is saved or replaced after every node, so it always holds the latest state, never a history. The first row has finished triage and will fetch the order next. The second is Dana's run, paused at the gate and saved with no next node.

Option 2, only T-1002's row. It has a next node, so the restart knows where to pick up. Dana's run has none on purpose: it waits for a person, and a restart isn't a person. Option 1 is tempting because "unfinished means resume", but resuming a paused run would skip the human decision. The next slide shows the line of code that makes the difference.

Idea 2On restart, unfinished runs carry on; a paused run waits

On startup, the service asks the database:

SELECT state_json, next_node FROM runs
WHERE status NOT IN ('completed', 'failed', 'awaiting_approval')

Each row it finds restarts at its next node, with the saved state.

  • T-1002 carries on at fetch_order_data. Triage doesn't run again.
  • Dana's run stays at the gate until someone clicks approve or reject.

When the service starts, app.lifespan calls graph.resume_stuck_runs, and store.find_resumable runs the query on the slide: every run that isn't finished and isn't waiting for a person. That leaves queued, running, needs_repair and executing. Each row restarts in its own thread at its saved next node, with its saved state, and writes a run.resumed line to the log.

So T-1002 picks up at fetch_order_data and doesn't pay for triage again. awaiting_approval is left out on purpose: restarting Dana's run would skip the person who is supposed to decide on her $79.99. In the code the query says NOT IN (?, ?, ?) and fills in the three statuses.

PredictThe server dies in the middle of planning

  • A run has finished normalize_ticket, triage and fetch_order_data.
  • The server dies while generate_resolution_plan waits for the LLM.
  • You restart. Which nodes run again?
  • Which LLM call do you pay for twice?

Work it out from the save rule. The last save happened after fetch_order_data, and it recorded the planner as the next node.

Only generate_resolution_plan runs again, then everything after it as normal. You pay for the planner call twice, about $0.0005: its first answer was in memory and never saved. "Everything reruns" is how a script behaves. A node can't pick up halfway through its LLM call either, because an HTTP request can't be resumed, so a crash costs at most the node that was running. The second plan may differ from the first, which is fine: nobody saw the first. One detail: cost_usd won't show the double charge, because the first call's cost was only in memory too.

Idea 3Polling, next to a stream of events

Polling: ask again and again

GET /runs/3f9c…  "running"
GET /runs/3f9c…  "running"
GET /runs/3f9c…  "running"
GET /runs/3f9c…  "awaiting_approval"

A stream: one request, it keeps writing

id: 4
event: node.started
data: {"node": "triage"}

id: 5
event: node.completed
data: {"node": "triage", ...}

An event stream is a normal HTTP GET whose response doesn't end. The server writes a few lines per event, then a blank line. It only goes one way: server to screen.

Two ways for a screen to follow a run. Polling: ask GET /runs/{id} again and again. You get "running" many times and still see each change up to one interval late. A stream: one GET /runs/{id}/events whose response never ends. For each event the server writes an id: line, an event: line and a data: line of JSON, then a blank line, and the screen gets each change as soon as it is saved. It only goes from server to screen, which is all a viewer needs. The standard is called Server-Sent Events (SSE).

Triage starts at id 4 because events 1 to 3 are normalize_ticket starting, the status changing to running, and normalize_ticket completing. The ids are what make reconnecting work (slide 18).

Idea 3What may reach the screen mid-run: progress, never half a plan

Stream progress, never half-finished machine output.
Say when a run ends, with an event. Never let a closed connection mean "done".
  • Only the customer reply streams word by word. Half a sentence is still readable.
  • The plan arrives once, whole and checked, in the last event.

Half a plan on an agent's screen: {"actions": [{"type": "issue_ref. Is that a refund? For how much? This is incident #3, the hook.

This slide is the streaming contract: the rules for what may reach a screen while a run is in progress. People may watch prose being typed: half a sentence is readable, and nobody acts on it. Programs only get finished, checked results: the plan arrives once, whole, inside run.completed, after validate_plan has passed it. The red box is why. Half a plan is useless to a program and misleading to a person, and a plan can still fail the rules and be repaired, so a streamed plan could show a refund that never happens.

The end of a run is always an event, run.completed or run.failed. A closed connection never means done. In the code, events.py lists the seven event types, and only draft_customer_reply sends reply.delta. The reply is written after execute_actions, so it describes what was actually done.

Idea 3Reconnecting: the refresh test

The agent's Wi-Fi drops after event 7. The browser reconnects by itself and gets 8 onwards. The log records that the viewer left. The run never noticed.

  • The run lives in a background thread and in SQLite, never in the connection.
  • Every event is saved with a number (1, 2, 3, …) before it is sent.
  • A viewer that comes back says "the last one I saw was 7". The server sends 8, 9, 10…, then carries on live.

The run was never in the connection. It lives in a background thread and in SQLite. Every event gets a number within its run (1, 2, 3, ...) and is written to the events table by events.publish before any screen sees it. The stream endpoint, run_events in app.py, only reads that table. So when a viewer comes back and says "the last one I saw was 7", the server reads the events after 7, sends them, then carries on live. The viewer leaving is written to the log as stream.disconnected, and the run doesn't notice.

The header that carries the "7" is Last-Event-ID. A browser's EventSource sends it by itself when it reconnects; with curl you add it yourself. No header means everything from event 1.

Five words from today, each with its plain meaning and where it lives in the code. The one worth reading twice is enum: a field that may only hold values from a fixed list. In Deskhand the enum is a Literal[...] type on status, not Python's Enum class, but it does the same job: a status off the list is rejected when the state is built or read back from the database.

UPSERT is SQL's "insert, or update if the row already exists". In store.save_state it is INSERT ... ON CONFLICT(request_id) DO UPDATE, which is why each run has exactly one row.

Three steps, three timescales. The request: submit_ticket in app.py checks the body, makes a 12-character request ID (the start of a random uuid4), saves the first state, starts the thread and returns, all in milliseconds.     internal_error_code: str | None = None  # a code for engineers
    cost_usd: float = 0.0                   # every LLM call adds its price
    node_latency_ms: dict[str, int] = Field(default_factory=dict)

A Literal[...] field is our enum. Pydantic rejects a value off the list when the state is built or loaded from runs.db. A plain assignment, state.status = "done", isn't checked.

The second half of TicketResolutionState. Each field answers a question you'd ask when a run goes wrong. Did it need a person, and why? requires_approval and approval_reasons, both set by code in validate_plan. What did the person decide? approval_status. Why did it fail? internal_error_code for engineers, user_visible_error for the customer. What did it cost? cost_usd, summed from every model call. Which node was slow? node_latency_ms.

If some code writes state.status = "done", the assignment succeeds: Pydantic checks values when an object is built, and this model doesn't turn on checking for assignments (validate_assignment). The bad value is saved, and the error appears when the row is read back, at GET /runs/{id} or at the next startup. That is one reason the nodes change the status in one place, _set_status.

The graphThe runner is a dict and a while loop

node = "normalize_ticket"                     # graph.py, simplified
while node not in (None, PAUSE):              # PAUSE: wait for a person
    emit("node.started", {"node": node})
    try:
        next_node = NODES[node](state, emit)  # one job; returns the next name
    except Exception:                         # also records a code from errors.py
        next_node = "handle_failure"
    store.save_state(state, next_node)        # the UPSERT into runs.db
    emit("node.completed", {"node": node, "latency_ms": ...})
    node = next_node

validate_plan returns "approval_gate" for T-1001 and "execute_actions" for T-1004.

The whole runner, simplified from graph.run: a name, a loop, and a dict of functions (NODES, at the bottom of nodes.py). Each turn: announce the node started, call it with the state, save, announce it completed, move to the name it returned. The loop never decides where to go. Each node's own code does, with ordinary if statements; the model fills in the state but never picks the next node. A node returns the next name, PAUSE to wait for a person, or None to stop, and any exception routes to handle_failure.

Two details in the real file: node.completed goes out after the save, so a screen never sees a node as done before it is on disk, and an error inside handle_failure itself ends the run instead of looping.

Five endpoints, all in app.py, and two ways to look at a run. GET /runs/{id} is pull: it returns the saved row, the state plus next_node, and is safe to call any time. The event stream is push: the live view of the same run. Because the state is always in the database, a refresh or a dropped connection costs nothing; ask again.

POST /approve on a run that isn't awaiting_approval returns 409 Conflict, so a finished run can't be approved again. It isn't airtight: two approvals sent at almost the same moment can both pass the check, because the status changes only when the resumed run saves its next node. ReferenceThe event stream, by its real names

  • The standard is Server-Sent Events (SSE). Browsers read it with EventSource, which also reconnects by itself.
  • On reconnect the browser sends Last-Event-ID. The server reads WHERE seq > 7 from the events table and sends 8, 9, 10…, then carries on live.
  • The disconnect is logged as stream.disconnected with code STREAM_DISCONNECTED in logs/runs.jsonl.
curl.exe -N -H "Last-Event-ID: 7" http://localhost:8000/runs/<request_id>/events

The real names, for reading the code. The standard is Server-Sent Events (SSE). Browsers read it with the built-in EventSource object, which reconnects by itself and sends a Last-Event-ID header with the last id it received. run_events in app.py reads that header and calls store.events_since, which runs WHERE seq > 7 on the events table: that one query is the whole replay. Then it keeps reading every 0.25 s for new events.

The curl line does the same by hand: -N turns off curl's buffering so lines appear as they arrive, and -H sends the header. A viewer leaving is logged as stream.disconnected, with the last id it was sent.

ResilienceRetry, repair, or stop: pick by error type

Retry

Order API timeout, connection error, or 5xx. It may work next time. 5 s timeout, 2 retries, waiting 0.5 s then 1.0 s.

Repair

Bad LLM output or a broken rule. Asking the same way repeats the mistake, so send the error back. Triage: 1 repair. Plan: 2.

Stop cleanly

LLM rate limit or timeout in 02: a code from errors.py, run.failed, and a safe message.

3 tries × 5 s + 0.5 s + 1.0 s = 16.5 s, then TOOL_ORDER_API_TIMEOUT. Do this sum before production does it for you.

The error decides what happens next, and there are three answers. Retry when the next attempt might work: an order API timeout, a refused connection or a 5xx. _order_api_call in nodes.py waits up to 5 s per attempt and retries twice, after 0.5 s and then 1.0 s. A 4xx is an answer, not a glitch, and isn't retried. Repair when asking the same way would get the same mistake: malformed model output, or a broken rule. The error goes back to the model; triage gets one repair, the plan two. Stop cleanly when neither helps: an LLM rate limit or timeout (the SDK has already retried) ends with a code, run.failed and a safe message.

Incident #4 happened because v1 retried everything the same way. The 16.5 s sum is the worst case; a stopped mock API refuses the connection at once, so that run fails much faster.
