1 · ContextOne model, three kinds of tool, one loop

Autocomplete

Suggests the next lines. You check before you press Tab.

Chat

Answers; you paste code in. You check before you paste.

Agent

Opens files, edits, runs commands, decides what's next. You check after: a whole diff.

A coding agent is a model in a loop with tools. It repairs against whatever check exists. No tests, and the loop stops at "it runs", not at "it's right". Copilot, Cursor, Claude Code, Codex: all of them are this, in an editor, a plugin or a terminal.

Most assistant products offer three kinds of help. Autocomplete suggests the next lines while you type; you check each suggestion before accepting it. Chat answers questions and writes code you paste in yourself. A coding agent is a model in a loop with tools: it opens files, edits them, runs commands such as pytest, reads the output and decides what to do next, until it judges the task done. The further right, the more it changes before you look, so an agent is checked afterwards, as a whole set of changes. The diagram is the agent's loop; the dashed arrow is the part that matters. It keeps going until its check passes, so with no tests the only check is "the code runs". Copilot, Cursor, Claude Code and Codex all work this way; the brand changes nothing in this deck.

1 · ContextEverything it knows is in its context

In the context window

  • Its system prompt
  • Your rules file, your messages
  • Files it chose to open
  • The output of every command it ran

Not in it

  • Files it never opened
  • Runs and logs it never read
  • Why you want the change
  • Yesterday's conversation

A small project fits in it whole. A large codebase doesn't: the agent searches, reads what it chooses, and can choose wrong.

Could it point at the line? When it tells you how something works, ask which file and which line. If it can't, it guessed. /context shows what it has actually read.

Session 1 called everything a model gets in one call its context window. A coding agent has one too. In it: the tool's system prompt (its built-in instructions), your rules file and messages, the files the agent decided to open, and the output of every command it ran. Not in it: files it never opened, logs it never read, your reasons. A small project fits whole; a large codebase does not, so the agent searches and picks, and can pick wrong. The habit for the whole session: when the agent states a fact about the code, ask it to point at the file and line that holds it. If it cannot, treat the answer as a guess. Context engineering is choosing what the agent reads before it acts: what you put in its context, what you point it at, what you keep out, and when you clear it.

The spec

Pointers

Clearing

Context engineering is the practice of deciding what the agent reads before it acts. The four levers on the slide: the rules file, a file in the repo the agent reads at the start of every session (next slide); the spec, a written description of this one task (block 2); pointers, naming the file, pasting the log line or linking the document you want it to read first; and clearing, starting a fresh session per task and for the review, because a full context window gets summarised by the tool (Claude Code calls this compaction) and loses detail. Two costs to remember: everything in the context is sent to the model on every turn, so it costs tokens each time, and anything in it can change what the agent does. The prompt injection from Session 2's T-1006 works just as well if it arrives in the output of a command the agent ran.

A rules file is a text file committed in the repo that the coding agent reads at the start of every session. The agent remembers nothing between sessions, so this file carries your team's conventions. The shared name is AGENTS.md, read by Codex, Cursor, Copilot's agent and others. A spec is a short written description of what the code must do, written before the agent types. 2 · The specTests are how the agent checks its work, so you choose them

The loop exits when its checks pass. Give it tests and it loops against your tests; give it nothing and it loops against its own guesses. You choose the test list, in plain sentences; it types the tests.

  1. Tests first, and they must fail first. A test that passes before the code exists checks nothing.
  2. "Don't change the tests" goes in the prompt. A test rewritten to pass is a finding erased.
  3. Make every test fail once. Break a line, see red, undo, see green. assert result is not None stays green with the repair loop deleted.

In the build: the spec's "Done when" named both test files and what each covers, and listed what the tests don't cover yet, to be checked by hand. Say what isn't tested, out loud.

The agent's loop stops when its checks pass, so the tests define "done", and you choose them: a test list is the behaviours you want locked down, written as plain sentences before any code; the agent turns each into a test. Three rules: tests first, failing first, because a test that already passes checks nothing; "don't change the tests" in the prompt, because an agent with a failing test will happily rewrite the test instead of the code; and make every test fail once on purpose, because a test that cannot go red proves nothing (assert result is not None survives the repair loop's deletion). The Logs page spec shows the honest version of "done": it names the two test files and what each checks, and lists what is not covered yet (the page's filters and messages, the colours' contrast), to be checked by hand.

3 · PermissionsHow much it may do without asking

Ask (the default)

Every edit and every command waits for your yes. Slow, and you see everything.

Accept edits

Edits go in. Commands still ask. The mode for a task with tests behind it.

Full auto

Nothing asks; it runs to the end. Claude Code: bypass permissions, or YOLO.

2025's habit was a yes to every step; 2026's is full auto, with loops that run for hours. The question is the same: what has to be true before you loosen its permissions?

Loosen them only as far as your automatic checks reach. Rewind exists in every tool, and git is the one that survives the session.

Claude Code adds plan mode (no edits) and auto (a second model screens each action). Shift+Tab cycles them.

Every coding agent has permission modes: how much it may do before it asks you. The strictest, and usually the default, is ask: the agent waits for your approval before each edit and each command. In the middle, accept edits: file changes go in without asking, commands still wait. The loosest is full auto: nothing asks and the agent runs until it decides it is done. Claude Code calls this mode bypass permissions, its nickname is YOLO, and the flag that enables it has "dangerously" in its name. Claude Code has two more modes: plan mode, where the agent reads and proposes but does not edit, and auto, where a second model screens each action before it runs. The rule for choosing: loosen the permissions only as far as your automatic checks reach. Every tool can rewind the agent's edits (in Claude Code, Esc Esc), but rewind does not cover what a command did; git does.

3 · PermissionsFour safeguards, and the worry each one removes

Tests

The loop's exit condition: what "done" means. Without them, done means "it runs".

Git

Small commits, a branch per task, rewind. What "undo" means, whatever the agent did.

Hooks

A command your tool runs on an event, every time. A check the agent cannot skip, guarding what it cannot change.

A reviewer

A colleague, or another agent in a fresh session. The one who wrote it grades its own homework.

Full auto needs a sandbox: a container or a cloud session with no keys and no production access. Full auto on your laptop next to your .env is the risk, not the mode.

We build the hooks now. The review is tonight's step 4, by hand.

Four safeguards make a looser permission mode safe. Tests are the agent's exit condition: they define "done". Git is "undo": small commits, a branch per task, and rewind, which together cover anything the agent did. A hook is a command your tool runs automatically on an event (before a command, after an edit, when the agent is about to stop); it runs every time, so it is a check the agent cannot skip. A reviewer in a fresh session, a colleague or a separate agent, catches what the author cannot, because the agent that wrote the code reviews it with the same context that produced it. Full auto needs one more thing: a sandbox, a container or cloud session with no API keys and no access to production. Running in full auto on your own laptop, next to your .env file, is the risk.

One rule, four places: the rules file asks, the spec repeats it, a test checks the result, a hook checks every edit. Cursor and Copilot have hooks too; a pre-commit hook and CI are the same check, later.

A hook is a command your tool runs automatically on an event. The two from the build were written in a separate session and live in slides/demos/session-03/class-hooks/. guard_env.py is a PreToolUse hook: it runs before every read, search, edit or shell command, and if the call names a .env file it exits with code 2, which blocks the call and hands the reason to the agent. no_innerhtml.py is a PostToolUse hook: it runs after every edit, when the file is already saved, so it cannot block; exit 2 sends its message back and the agent fixes its own code in the same turn. Both match text, so both have false positives: guard_env also blocks a git commit whose message mentions the file. A false positive costs a rephrase; a missed key costs a rotation.

The line is saved: a hook that runs after the edit cannot undo it. The hook prints the offending line and exits 2, the agent reads it and rewrites the line with textContent. The same rule lives in four places: the rules file (guidance), the spec's limits (this task), test_logs_js_never_writes_markup (the result), and this hook (every edit).

# .claude/settings.json
{"hooks": {
  "PreToolUse": [{"matcher": "Edit|Write|MultiEdit", "hooks": [{"type": "command", "command": "python .claude/hooks/protect_tests.py", "timeout": 30}]}],

# .claude/hooks/protect_tests.py: existing tests and spec.md may not change mid-run; a new test file may be written
payload = json.load(sys.stdin); target = Path(payload["tool_input"].get("file_path", ""))
is_contract = "tests" in [p.lower() for p in target.parts] or target.name.lower() == "spec.md"
if is_contract and not (payload["tool_name"] == "Write" and not target.exists()):
    print(f"Blocked: {target.name} is part of the contract (tests/ and spec.md). "
          "Change the code to satisfy the tests, or stop and say what in the spec should change.", file=sys.stderr)
    sys.exit(2)                                   # blocked, and it reads this

# .claude/hooks/pytest_gate.py: three tries, then it reports instead of looping
counter = Path(__file__).with_name(f".gate-{payload.get('session_id', 'default')}")
tries = int(counter.read_text()) if counter.exists() else 0
run = subprocess.run([sys.executable, "-m", "pytest", "-q", "-x"], capture_output=True, text=True)
if run.returncode == 0:
    counter.unlink(missing_ok=True); sys.exit(0)    # green: it may stop
if tries >= 3:
    counter.unlink(); print("Still red after 3 tries. Stopping; report it.", file=sys.stderr); sys.exit(0)
counter.write_text(str(tries + 1))
print("Tests are red, so this is not done.\n" + "\n".join((run.stdout + run.stderr).splitlines()[-25:]), file=sys.stderr)
sys.exit(2)                                       # red: the stop is blocked, and it reads this

Exit code 2 is the convention: "blocked, here is why". Exit 1 is an ordinary error and does not block. Start the agent from the folder that holds .claude/, with your venv active, so python is the one with pytest.

Tonight's two hooks, condensed; the handout prints the full files to copy into work/my-triage/.claude/. They guard a different thing from the class's two on slide 20: these protect the tests, the contract the agent works against. The settings file registers the contract hook for every Edit or Write and the Stop hook for the Stop event. The contract hook blocks edits to existing test files and to spec.md (a brand-new test file may still be written, so "tests first" works) and prints the reason, which the agent reads. The Stop hook runs pytest when the agent wants to stop: green exits 0 and lets it stop; red prints the last lines of output and exits 2, which blocks the stop. A small counter file limits that to three tries per session, after which the hook exits 0 with a message, so an unfixable test ends in a report rather than a loop. Start the agent from the folder that holds .claude/, with your virtual environment active, so that python is the one with pytest installed.

ReferenceWhere agents go wrong: six patterns to look for

Plausible but wrong

Reads perfectly, fails one case: the summary without its FAILED row.

Invented names

Calls llm.complete(). The real one is structured_completion.

Does too much

"While I was there, I renamed sentiment to tone."

Rules in another file

errors.py says every error has a code. It writes raise ValueError, and main.py crashes on one bad ticket.

Done without running

"Done" with no test run, as in the hook. A rules line and a hook both catch it.

Prompt injection

Pastes ticket text into instructions. Follows a comment in a file as if it were your request.

Top row: slips you'll meet tonight. Bottom row: slow your review down when correctness depends on something it didn't read, or read something it shouldn't have obeyed.

Six recurring agent mistakes. Top row, the everyday slips: code that reads well and fails one case (the summary without its FAILED row), a plausible function name that does not exist, and unrequested changes made "while I was there". Bottom row, the ones that need a slower review: a convention that lived in a file the agent did not read (every Deskhand error carries a code; a bare ValueError escapes main.py's handler and crashes the batch), "done" declared without running anything, and prompt injection: text in its context that steered it, whether customer text pasted into a prompt or an instruction found inside a file and obeyed as if you had written it.
