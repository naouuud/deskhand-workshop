Logs: every checkpoint, as one live stream

The lines checkpoints 01 to 04 append to their logs/runs.jsonl, from the lab, a terminal, curl and the evals alike. Click a request id to follow one run, an event or a code to filter on it.

Every line here was written by the checkpoint's own obslog.log_event: one JSON object per line, with a ts and a request_id. The services write theirs through events.publish, which stores the event for the SSE stream first. The level and the one-line message are the lab's reading of the event name; the log itself has neither. That request_id is what turns thousands of interleaved lines into one run you can read.

Orders: what the order system really holds

The source of truth to check a run against. Click an order for its details.

A service sees an order only through GET /orders/{id}, one at a time. This page reads every order the same way, with one difference: it sends X-Chaos: none, so a chaos mode never hides the store. The refunds are GET /refunds. Nothing here writes: the lab never pays a refund of its own.

Saved state: what a service's runs.db holds

One row per run, saved after every node, read straight from the checkpoint's SQLite file. The headline says which runs a restart would pick up. Click a run for its row, its stored events and, on LangGraph, every step.

The log is history for people; the row is the current state a machine resumes from. This page reads runs.db read only, as sqlite3 would. Which runs a restart picks up is not the lab's guess: it asks the checkpoint's own store.find_resumable(), the call resume_stuck_runs makes when the service starts. Try it: start a run, stop the service in Setup mid-run, and watch the row stay behind with its next node.
